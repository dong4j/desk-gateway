# 从软件 I²C 回退到硬件 I²C 的排查记录

| 项 | 内容 |
|---|---|
| 文档编号 | DG-INV-001 |
| 日期 | 2026-08-12 |
| 已确认稳定基线 | `3269faa` |
| 适用硬件 | ESP32-S3 + yourdesk_v1 控制盒 |
| 最终决策 | 控制盒侧只用硬件 I²C Slave 响应 `0x24`；停止解析控制盒高度 |

## 1. 问题现象

新固件能够显示控制盒返回的真实高度，但按住升高时桌子反复启动、停止。下降一度较为流畅，
后来随着软件 I²C 时序修补增加，也出现过相同回归。Web、REST、BLE 和旋钮均能复现，说明
问题不属于某一个客户端入口。

排查期间已经依次排除了：

- Web 指针事件提前发送 STOP；
- REST/BLE 长按续租超时；
- 最高安全高度提前触发；
- 高度帧未及时更新导致主动停止；
- 档位闭环或童锁策略主动停止。

日志中运动期间没有对应的 `DR=0x2E`，但桌子仍会短暂停止，说明 ESP32 没有主动切换为
停止键码，而是控制盒没有持续读到完整的上升键码。

## 2. 找到可用基线

真机重新烧录提交 `3269faa` 后得到明确结果：

- 按住升高连续运行；
- 按住降低连续运行；
- 松手后正常停止；
- 不存在当前版本的断断续续现象。

这个提交不解析真实高度，只使用 ESP32-S3 硬件 I²C Slave 响应按键地址 `0x24`。业务代码
只更新当前键码，ACK、移位和总线时序都由 ESP32-S3 I²C 外设完成。

```text
上升：0x47
下降：0x4F
停止：0x2E
```

## 3. 回归从哪里开始

提交 `f9506a0` 为了同时处理按键和高度，将控制盒侧通信从硬件 I²C 改成 GPIO 中断驱动的
软件 I²C：

```text
0x24       按键状态
0x34-0x37 控制盒写给数码管的四个显示位置
```

ESP32-S3 的一个硬件 I²C Slave 只能配置一个精确地址。为了在同一组 CLK/DAT 上同时响应这
五个地址，项目开始逐个处理 SCL/SDA 边沿，并由软件决定每个 bit 何时拉低或释放 DAT。

这不是算力不足，而是关键时序从硬件外设转移到了实时软件中断。Wi-Fi、BLE、日志、任务调度
以及 GPIO 自身产生的 DAT 边沿，都可能让状态机错过或误判一次总线边沿。

## 4. 日志证据

故障版本的诊断日志曾出现：

```text
key_tx=102/8 abort=94
key_tx=164/8 abort=156
key_tx=128/4 abort=124
```

三段合计发起 394 次按键响应，仅 20 次完整发送，374 次中途被打断，完成率约 5%。控制盒
只有偶尔能读到完整的 `0x47`，因此实际行为变成：

```text
完整读到 0x47 -> 上升
本轮读取失败   -> 控制盒认为按键未持续
再次读到 0x47 -> 继续上升
```

这正是桌子断断续续的直接原因。下降使用 `0x4F`，bit 排列不同，在同一软件状态机中表现可能
相对好一些，但并不能证明软件 I²C 控制链路可靠。

## 5. 为什么停止继续修补软件 I²C

软件 I²C 后续已经尝试过边沿过滤、START/STOP 保护、ULP 采样、任务优先级调整和发送阶段
保护。这些修改有时改善一部分日志，但没有恢复到 `3269faa` 的连续真机行为，而且曾使原本
正常的下降路径回归。

从软件架构看，为了增加高度 telemetry，项目重写了已经稳定的 command transport。继续在
同一实现上叠加时序规则，会让升降安全性依赖越来越复杂的中断状态机，不符合本项目对核心
运动链路的要求。

因此不再以“软件 I²C 同时负责按键和高度”为产品方案。

## 6. 最终架构决策

同一块 ESP32-S3 继续承载全部上层功能，但底层职责拆分：

```text
ESP32-S3
├── Web / REST / BLE / 童锁 / 来源权限
├── I2C0 硬件 Slave @0x24
│   └── 只负责上升、下降和停止
└── I2C1 硬件 Master
    └── 后续连接 TOF200C，提供真实桌面高度
```

控制盒侧不再响应 `0x34-0x37`，也不再解析数码管段码。TOF200C 到货并完成校准前：

- Web、手机和 Watch 保留高度区域，但显示 `—`；
- `height_known=false`，禁止使用模拟高度冒充真实高度；
- 手动升高、降低和 STOP 继续工作；
- 档位 1/4 的高度闭环和最高安全高度暂不可用；
- 童锁、REST/BLE 来源权限和断连停止继续生效。

TOF200C 接入后，高度由独立传感器驱动提供，不再改变控制盒 `0x24` 的通信实现。

## 7. 实施范围

本次只做以下修改：

1. 默认关闭 `CONFIG_DESK_YOURDESK_SOFT_I2C_MULTI_ADDRESS`；
2. 保持实验性 GPIO 高度嗅探关闭；
3. 恢复已有的 ESP-IDF 硬件 I²C Slave `@0x24` 路径；
4. 保留现有上层 API 和客户端 UI；
5. 将高度能力声明为不可用，等待 TOF200C 驱动；
6. 不实现新的模拟高度，不继续调整软件 I²C 时序。

软件多地址实现可以暂时保留为历史实验代码，但不得进入默认固件；确认硬件 I²C 真机验收后，
再单独决定是否删除。

## 8. 真机验收标准

烧录后必须满足：

- 启动日志出现 `I2C slave @0x24 SCL=4 SDA=5`；
- 启动日志不出现 `software I2C addrs=0x24,0x34-0x37`；
- Web、REST、BLE 分别按住升高和降低，运动全程连续；
- 松手或显式 STOP 后立即停止；
- 高度显示为未知，不出现 `SIM` 或控制盒 digit 解析值；
- 童锁开启后所有入口拒绝运动，STOP 始终可用；
- 连续运行过程中无 `key_tx abort` 类软件 I²C 诊断。

自动化构建和主机测试只能证明代码路径可编译，最终结论必须以真实桌子验收为准。
