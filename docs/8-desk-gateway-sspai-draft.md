# 我的升降桌改造：破解原厂面板，接入多种控制方式

我最初只想让桌上的旋钮控制升降桌。

顺时针转，桌子升高；逆时针转，桌子降低；按一下，停止。操作听起来很简单，真正动手时才发现，我连原厂面板和控制盒之间说的是什么都不知道。

这件事在我的待办里放了很久。最近辞职在家，时间宽裕了一些，我才把控制面板拆下来。之前看过少数派的《[从零开始，改造一张可以用 Siri 控制的升降桌](https://sspai.com/prime/story/diy-a-siri-enabled-standing-desk)》，也研究过开源项目 [Upsy Desky](https://github.com/tjhorner/upsy-desky)。思路都能借鉴，协议却对不上我的桌子，现成方案没法照搬。

我原本以为找一块开发板、接几根线就能收工。后来旋钮还没接上，桌子先被我拆了。

> [图片占位：升降桌、桌面旋钮和桌下临时接线同框，作为题图]

## 一、我原本只想给桌子接一个旋钮

### 原厂面板够用，但不够顺手

我的升降桌只能通过原厂面板控制。面板上有上升、下降和四个档位键，单击档位可以前往保存的高度，长按则会覆盖原来的设置。功能不算少，也谈不上难用，只是每次调节都得伸手去桌边找按键。

坐下和站起是我一天里会重复很多次的动作。如果手正放在键盘和鼠标上，桌面的旋钮显然比桌边那排按键顺手。尤其是桌下塞进抽屉和线材以后，原厂面板的位置更显得有些别扭。

### 从一个现成旋钮想到更多控制方式

我最早是从 zFrontier 上的一个[旋钮控制方案](https://www.zfrontier.com/app/flow/1b0Jwj5y6wOk)得到启发。桌上正好有一个闲置旋钮，拿它控制升降很合适。

继续往下想，旋钮其实只是一个入口。键盘可以发快捷键，手机可以走蓝牙，浏览器可以调局域网接口，手表也能用表冠控制。只要我能复现原厂面板发出的指令，后面的控制方式就不用各自折腾一套硬件。

### 现成的开源项目为什么不能直接用

少数派那篇 Siri 升降桌文章和 Upsy Desky 都给了我不少启发，尤其是“在控制盒与面板之间加一层”的思路。不过升降桌没有统一的面板协议，不同品牌甚至同一品牌的不同批次都可能不一样。

Upsy Desky 适配的是另一类控制盒，我这张桌子的面板从 RJ45 插头里只引出了四根线。接口长得相似，不代表里面跑的是同一种数据。要想继续，只能先弄清这四根线的用途。

## 二、先拆开面板，看看四根线里跑的是什么

### RJ45 只是一个插头

原厂面板使用 RJ45 插头，很容易让人联想到网线。拆开以后就没那么神秘了。电路板背面有四个测试点，分别标着 `3.3V`、`GND`、`CLK` 和 `DAT`。我用万用表逐根量过，最终确认红线供电、白线是时钟、绿线接地、黑线传数据。

RJ45 在这里只是一个便宜又牢靠的插头，和以太网没有关系。这个结论很重要，后面的临时接线、双接口转接板以及 PCB 都会沿用它，但它绝对不能接进电脑、交换机或者普通网络设备。

> [图片占位：原厂控制面板背面，标出四个测试点和 RJ45 线色]

### 面板上的 TM1650

面板正面还有一颗 TM1650。这颗芯片既能驱动数码管，也能扫描按键，常见于各种带数字显示和按键的廉价面板。看到型号以后，协议范围已经缩小了不少：`CLK` 和 `DAT` 很可能就是一组 I²C 总线。

“很可能”还不够。控制盒和面板谁主动发起通信，按键值怎么编码，高度又从哪里来，这些都得从真实波形里找答案。

> [图片占位：控制面板正面特写，圈出 TM1650 和数码管]

### 第一次抓包基本白抓了

我为此买了一台逻辑分析仪。接线并不复杂：原厂面板继续与控制盒正常连接，分析仪只从测试点引出 `GND`、`CLK` 和 `DAT` 三根探针。分析仪不接面板的 3.3V，也不给桌子供电，它只在旁边听。

第一份波形几乎白抓了。20 kHz 的采样率能看出线上有高低变化，放大以后却读不出完整数据。我起初还怀疑接线有问题，来回检查了几次才把采样率提高到 12 MHz。PulseView 终于能稳定解码，原来糊成一片的方波也有了清楚的地址和数据。

我重新录了静置、按住上升、按住下降、单击档位和长按保存。为了找高度数据，又补录了从 64 cm 一路升到 129 cm 的几段长包。抓长包时还得在旁边记下桌子当时显示的数字，不然文件放到第二天再看，很容易一头雾水。

> [图片占位：20 kHz 与 12 MHz 两次采样的波形对比]

## 三、控制盒一直在问，面板只负责回答

### 谁是 Master，谁是 Slave

抓包结果和 TM1650 的工作方式能对上。控制盒是 I²C Master，负责产生时钟并发起读取；面板是 Slave，等着控制盒来问。按键通道使用 7-bit 地址 `0x24`。

原厂面板不会主动发出一条“开始上升”的消息。控制盒大约每 3.7 毫秒轮询一次，面板只负责回答“现在按着哪个键”。只要它连续回答上升，桌子就继续升；一旦回答空闲，桌子马上停下。

### 上升、下降和松手分别是什么

我把不同操作的抓包逐个对照，先确认了最重要的三个值：空闲和松手返回 `0x2E`，按住上升返回 `0x47`，按住下降返回 `0x4F`。

目前确认的键码如下：

| 操作 | 面板返回值 |
| --- | --- |
| 空闲、松手 | `0x2E` |
| 按住上升 | `0x47` |
| 按住下降 | `0x4F` |
| 档位 1 单击、长按 | `0x17`、`0x57` |
| 档位 4 单击、长按 | `0x2F`、`0x6F` |

档位 2 和档位 3 没有可靠抓包，所以我没有照着数字规律往下猜。桌子毕竟真的会动，少两个暂时不能用的档位没什么，发错指令则可能得不偿失。

> [图片占位：上升、下降和空闲三个键码的波形对比]

### 被我当成干扰的高度数据

高度也在这两根线上，只是不在按键返回值里。控制盒会把当前高度转成数码管段码，再写入 `0x34` 至 `0x37` 四个地址。每个地址对应一个数码管位置。

最开始我把这些写入当成了电机运行时的干扰，顺手过滤掉了。后来拆开面板确认 TM1650，又拿 64 cm 和 102 cm 的静止数据对照，才发现被我丢掉的正是高度。

这次误判是我先入为主。我一直在按键通道里找一个现成的厘米数，没想到控制盒发来的只是“该点亮数码管的哪几段”。段码表整理出来以后，64、82、102、121 等高度都能从抓包中还原。

> [图片占位：64 cm 的面板显示与 `0x34` 至 `0x37` 段码标注]

## 四、ESP32 第一次把桌子升了起来

### 用 ESP32-S3 顶替原厂面板

手上有了键码，我找出一块闲置的 ESP32-S3，让它先顶替原厂面板。控制盒仍然是 Master，ESP32-S3 只在地址 `0x24` 上等待读取。网页里按住“上升”时，它向控制盒返回 `0x47`；松手时改回 `0x2E`。下降也是同一套逻辑。

这时我还没有急着接旋钮。先用 Web 页面发指令更方便排查，页面、网络请求、固件状态和串口日志都能分开检查。

### 日志没问题，桌子却纹丝不动

第一次上电测试，串口日志看上去很正常。点上升，当前键码变成 `0x47`；点下降，变成 `0x4F`。程序没有报错，桌子却纹丝不动。

我盯着日志看了半天，后来才意识到它只能说明程序准备好了哪个字节，不能说明控制盒真的从电线上读到了。软件里的状态没错，问题多半在软件外面。

### 补回两个电阻后，桌腿终于动了

我重新接回原厂面板测量，发现 `CLK` 和 `DAT` 各有一只约 `1.99 kΩ` 的上拉电阻。拔掉原厂面板时，这两只电阻也一起消失了。I²C 总线连可靠的高电平都没有，代码里的 `0x47` 自然送不到控制盒。

我从控制盒的 3.3V 分别接了一只 2 kΩ 电阻到 `CLK` 和 `DAT`。ESP32-S3 继续用 USB-C 单独供电，只与桌子共地。重新上电后，再按 Web 页面里的上升键，桌腿终于开始移动。

当时我没有接着试档位。我先来回验证了几次升高、降低和松手停止。能让桌子动起来只是第一步，能让它随时停下更要紧。

## 五、高度读出来以后，桌子反而不好用了

### 两组硬件 I²C 也不够处理五个地址

按键控制跑通后，我开始把高度解析搬进 ESP32-S3。离线分析已经能认出数码管段码，我本以为这一步只是把现成代码放进固件，真正动手才碰到 I²C 外设的限制。

ESP32-S3 有两组硬件 I²C 控制器。我的桌子却要求它在同一对 `CLK/DAT` 上处理五个 Slave 地址：`0x24` 用于按键，`0x34` 至 `0x37` 对应四个数码管位置。一个硬件 I²C Slave 只能配置一个精确地址，两组控制器也没法同时接住这五个地址。

这里容易说岔。升降加高度需要的是五个地址，不是五组 I²C 线。物理上从头到尾都只有一对 `CLK/DAT`。

### 改成软件 I²C 后，高度出现了

为了同时返回按键并接收高度，我把控制盒这一侧改成了软件 I²C。程序通过 GPIO 中断观察每一个时钟和数据边沿，自己判断 START、STOP、地址、数据和 ACK。

改完以后，高度很快出现在 Web 页面上。桌子运动时，页面里的数字会跟着变化。那一刻我以为最麻烦的部分已经过去，结果它只正常了很短一会儿。

### 上升开始一顿一顿

桌子的上升很快变得断断续续。它会升一小段，停一下，再接着升；下降最初还算流畅，继续修补以后也被拖下了水。

我先排查上层。Web 有没有提前发送 STOP，BLE 的运动租约有没有过期，高度刷新有没有误触安全上限，这些都查了一遍。日志里没有出现 `0x2E`，桌子仍然会停，问题只能继续往底层找。

### 394 次响应，只完整发出了 20 次

最后加上的计数很难看。三段日志里一共发起 394 次按键响应，只有 20 次完整发送，另外 374 次都在中途终止，成功率大约只有 5%。

这正好解释了桌子的动作。控制盒偶尔读到一个完整的 `0x47`，桌子就升一下；下一轮没读全，它便认为按键已经松开，于是停住。上层没有发出 STOP，软件 I²C 自己先掉了链子。

> [图片占位：软件 I²C 故障日志，标出 394 次发起、20 次完成和 `abort`]

### 继续修软件 I²C，还是保住已经稳定的升降

我又试了边沿过滤、START 和 STOP 保护、调整任务优先级，也尝试过用 ULP 辅助采样。有些改动能让某一段日志好看一点，换个场景又会复发。Wi-Fi、BLE、串口日志和任务调度随时可能挤进这段时序，继续打补丁只会让运动控制越来越难收拾。

最后我把这套方案撤了。为了多读一个高度，把已经稳定的升降链路改得摇摇欲坠，实在舍本逐末。

控制盒这一侧重新使用硬件 I²C Slave，只处理地址 `0x24`，ACK、移位和时序都交还给 ESP32-S3 的硬件外设。这条路径此前已经在真桌上跑过连续升降和松手停止；最近的整合固件刚切回硬件方案，还需要重新烧录复验。高度暂时留空，Web、手机和 Watch 上都显示一条横线，不拿估算值凑数。

### 把高度交给独立测距模块

高度准备换一条路解决。我计划在桌板下方安装 TOF200C，让它朝地面测距，再加上安装位置的固定偏移，算出桌面高度。ESP32-S3 的另一组硬件 I²C 会单独连接这个传感器，不再碰控制盒的按键总线。

这部分目前只是方案，模块还没有完成采购和真机验证。桌子的行程大约是 64 至 129 cm，传感器到货后要拿卷尺逐段校准，还得分别测试深浅地面、地垫、环境光和遮挡。数据稳定以前，档位闭环和最高高度限制都不会重新开放。

> [图片占位：TOF200C 安装位置草图，标出传感器到地面的距离和桌板偏移]

## 六、旋钮终于接上了

### 旋钮的升降和停止逻辑

绕了一圈，最初想要的旋钮总算能用了。

我用 Karabiner 把顺时针、逆时针和按下映射成三个闲置功能键，再由 Shell 脚本调用 ESP32-S3 的局域网接口。为了避免误碰一下桌子就突然动，第一个刻度只做准备，700 毫秒内出现第二个同方向刻度才开始升降。停止旋转后，最后一次指令的租约在大约 500 毫秒后失效，桌子自动停下。中途反向旋转则先停，再启动另一个方向。

这套操作没有原厂档位那么干脆，却很符合旋钮的手感。我不需要盯着高度数字，转到合适的位置松手就行。

### Web 和 iPhone 只是同一套控制的不同入口

同一套控制后来也接到了 Web、BLE 和 iPhone App。网页适合坐在电脑前使用，手机优先走 BLE，需要时再切到局域网。

这些入口最后都会调用 ESP32-S3 里的同一套升降和停止逻辑。童锁、来源权限、运动租约和断连停止也放在中枢统一处理。手机和网页共用一套规则，真出问题时也比较容易顺藤摸瓜。

### Apple Watch 还停在原型阶段

Apple Watch 的界面也做了一个版本。Digital Crown 很适合连续调节：正向旋转升高，反向旋转降低，停止旋转后发出 STOP。

手表端代码已经写完，单元测试和 Xcode 编译也通过了；真机配对、Crown 停止，以及它和 iPhone、Android 同时连接时的测试还没做完。因此它现在仍是一张原型图和一套待验收代码，还不能算已经交付的控制方式。

> [图片占位：旋钮、Web、iPhone App 和 Apple Watch 原型拼图]

### 为什么暂时没有继续接语音

语音同样可以复用局域网接口，不过我没有急着接 Siri 或 Home Assistant。没有可靠高度时，“切换到站姿”缺少闭环；只做“开始上升”又不如旋钮和实体按键踏实。

等测距模块跑稳以后，再把固定坐姿、站姿交给语音控制会更合适。现在先把桌子升得稳、停得住，比多一个入口重要。

## 七、现在还只是一块挂在桌下的开发板

### 原厂面板暂时被 ESP32 顶替了

目前的接法是让 ESP32-S3 顶替原厂面板，两者不能同时接在控制盒上。网页、手机和旋钮都曾在各自的开发阶段控制过真桌；最近把固件切回硬件 I²C 后，还要重新烧录做一次整体验收。无论使用哪个版本，原来的实体面板都得暂时退出。

这套接法用来验证协议没有问题，长期挂在桌下就有点顾此失彼。电脑关机、手机没电或者网络抽风时，桌边本来有一排现成按键，却因为改造不能用，怎么都算不上完整方案。

### 下一版需要两个 RJ45 接口

下一版会使用双 RJ45。北向接口连接升降桌控制盒，南向接口连接原厂面板，ESP32-S3 串在中间转发数据。平时原厂按键和高度显示照常工作；收到 Web、BLE 或旋钮指令时，网关再插入相应键码。

这样既不用牺牲实体面板，也能在原厂按键和无线命令撞车时做仲裁。童锁也要等这一步完成才名副其实。现在的童锁只能拦住 Web、REST 和 BLE，挡不住直接接在控制盒上的面板。网关真正串到中间以后，才能过滤面板的升降操作，同时保留 STOP。

> [图片占位：双 RJ45 数据路径草图，左边控制盒、中间网关、右边原厂面板]

### 双 RJ45 目前卡在哪里

双 RJ45 的代码已经写了一部分，实际透传还没跑通。两侧 GPIO、线序和上拉都量过，原厂面板一侧却缺一份可靠的全上电波形。之前录到的文件与现场电压对不上，不能硬拿来当依据。

等面包板接线整理好，我会重新以 12 MHz 采样率抓一次面板侧的上升操作。先确认控制盒、网关和原厂面板三者同时上电时的真实时序，再继续做透明透传和指令仲裁。

### 从一张桌子扩展到更多型号

如果双 RJ45 跑通，后面才轮到更多桌型。Upsy Desky 未必能直接控制我的桌子，但它把不同桌型协议拆开的办法很值得借鉴。

我现在把不同厂商的协议收在 Desk Driver 里，自己的桌子先使用 `yourdesk_v1`。以后碰到 UART、Loctek 或 Jiecang 协议，再分别补对应的 Driver。上层的 Web、手机、手表和蓝牙只认统一的控制接口，不需要跟着桌型重写。

### 第一次尝试画 PCB

最后是 PCB。现在桌下挂着开发板、杜邦线和电阻，能用归能用，看起来仍然是一套实验装置。我还没有完整画过这种板子，准备先把双 RJ45、USB-C 供电、ESP32-S3 最小系统和保护电路放进第一版原理图。

首版不追求小巧。接口别画反，测试点留够，焊完以后出了问题还能量，就算开了个好头。等协议和硬件都稳定下来，再考虑外壳、尺寸和批量制作。

> [图片占位：桌下现有开发板原型，以及第一版 PCB 的尺寸草图]

回头看，这件事和最初设想已经相去甚远。我只是想给桌子加一个旋钮，最后买了逻辑分析仪，拆了控制面板，记下一堆十六进制键码，还因为贪心读取高度，把稳定的升降功能折腾坏了一次。

旋钮这条控制链路已经在真桌上跑通过：转动时桌子跟着动，停手后它也会停。下一步先把原厂面板接回来，再处理高度和 PCB。至于把它做成一个真正的升降桌网关产品，等这些线不再挂在桌子下面时再说。

> 安全说明：本文记录的是我在自有设备上的协议分析和原型实验。升降桌运动可能夹伤人员或损坏物品，调试时应有人留在桌旁，并始终保留可靠的 STOP。文中的 RJ45 只是插头形态，不能接入电脑、交换机或普通网络设备。
