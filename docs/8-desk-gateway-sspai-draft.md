# 为了让旋钮控制升降桌，我买了一台逻辑分析仪

我最初只想让桌上的旋钮控制升降桌。

顺时针转，桌子升高；逆时针转，桌子降低；按一下，停止。想法很简单，真正动手时才发现，我连原厂面板和控制盒之间说的是什么都不知道。

这件事在我的待办里放了很久。最近辞职在家，终于有时间把控制面板拆下来。我先看了少数派的《[从零开始，改造一张可以用 Siri 控制的升降桌](https://sspai.com/prime/story/diy-a-siri-enabled-standing-desk)》，也研究了 [Upsy Desky](https://github.com/tjhorner/upsy-desky)。它们都能控制升降桌，可惜不能直接用在我这张桌子上。Upsy Desky 面向的是另一套通信协议，我的面板从 RJ45 插头里只引出了四根线。

于是我买了一台逻辑分析仪。

旋钮还没接上，桌子先被我拆了。

## 先把原厂面板拆开

我的升降桌只能靠原厂面板控制。面板上有上升、下降和四个档位键，单击档位可以前往保存的高度，长按则会覆盖原来的设置。功能不算少，只是所有操作都得伸手去桌边完成。

我最早是从 zFrontier 上的一个[旋钮控制方案](https://www.zfrontier.com/app/flow/1b0Jwj5y6wOk)得到启发。桌上正好有一个闲置旋钮，拿它控制升降很合适。继续往下想，键盘、手机、网页和手表其实都一样，它们只是发出指令的方式不同。只要能复现原厂面板的指令，后面的入口都好办。

原厂面板使用 RJ45 插头，很容易让人联想到网线。拆开后就没那么神秘了。电路板背面有四个测试点，分别标着 `3.3V`、`GND`、`CLK` 和 `DAT`。我用万用表逐根量过，最终确认红线供电、白线是时钟、绿线接地、黑线传数据。RJ45 在这里只是一个便宜好用的插头，和以太网没有关系。

面板正面还有一颗 TM1650。这个芯片很常见，既能驱动数码管，也能扫描按键。看到型号后，协议范围已经缩小了不少，但数据到底怎么走，还是要抓了再说。

> [图片占位：原厂控制面板正面和背面，标出 TM1650、四个测试点以及 RJ45 线色]

逻辑分析仪接起来并不复杂。我让原厂面板继续与控制盒正常连接，只从测试点引出 `GND`、`CLK` 和 `DAT` 三根探针。分析仪不接面板的 3.3V，更不会给桌子供电，它只在旁边听。

第一份波形几乎白抓了。20 kHz 的采样率能看出线上有高低变化，放大以后却读不出完整数据。后来把采样率提到 12 MHz，PulseView 才能稳定解码。我重新录了静置、按住上升、按住下降、单击档位和长按保存。为了找高度数据，又补录了从 64 cm 一路升到 129 cm 的几段长包。

抓长包时还得在旁边记下桌子当时显示的高度。否则一堆文件放到第二天，名字再清楚也容易看得一头雾水。

## 控制盒每隔几毫秒问一次按键

抓包结果和 TM1650 的工作方式能对上。控制盒是 I²C Master，负责产生时钟；面板是 Slave，等着控制盒来读取按键。原厂面板不会主动往外发送一条“开始上升”的消息，它只是不断回答“现在按着哪个键”。

桌子静置时，控制盒大约每 3.7 毫秒轮询一次。面板没有按键就返回 `0x2E`，按住上升返回 `0x47`，按住下降返回 `0x4F`。松手后，返回值重新变成 `0x2E`，桌子便停止运动。

我目前确认的键码只有这些：

| 操作 | 面板返回值 |
| --- | --- |
| 空闲、松手 | `0x2E` |
| 按住上升 | `0x47` |
| 按住下降 | `0x4F` |
| 档位 1 单击、长按 | `0x17`、`0x57` |
| 档位 4 单击、长按 | `0x2F`、`0x6F` |

档位 2 和档位 3 没有可靠抓包，所以我没有照着数字规律去猜。桌子毕竟真的会动，少两个暂时不能用的档位没什么，发错指令则可能得不偿失。

高度也在这两根线上，只是不在按键返回值里。控制盒会把当前高度转成数码管段码，再写到 `0x34` 至 `0x37` 四个地址。最初我把这些地址当成了电机工作时的干扰，浪费了不少时间。后来拆开面板确认芯片型号，又拿 64 cm 和 102 cm 的静止数据对照，才发现被我丢掉的正是高度。

这次误判说到底是先入为主。我一直盯着按键通道找一个现成的高度数字，没想到控制盒发来的只是“该点亮数码管的哪几段”。段码表整理出来以后，64、82、102、121 等高度都能从抓包中还原。

## 第一次让 ESP32 控制桌子

手上有了键码，我找出一块闲置的 ESP32-S3，让它顶替原厂面板。控制盒仍然负责发起通信，ESP32-S3 只在地址 `0x24` 上等着。网页里按住“上升”时，它向控制盒返回 `0x47`；松手时改回 `0x2E`。下降同理。

第一次上电测试，串口日志看上去很正常。点上升，当前键码变成 `0x47`；点下降，变成 `0x4F`。桌子纹丝不动。

继续盯着软件日志没有用。它只能说明程序准备好了哪个字节，不能说明控制盒真的从电线上读到了。我回头测原厂面板，才发现 `CLK` 和 `DAT` 各有一只 `1.99 kΩ` 的上拉电阻。拔掉面板时，这两个电阻也一起被拔掉了。总线连正常的高电平都没有，代码里的键码自然送不到控制盒。

我从控制盒的 3.3V 分别接了一只 2 kΩ 电阻到 `CLK` 和 `DAT`，ESP32-S3 仍然用 USB-C 单独供电，只与桌子共地。重新上电后，再按 Web 页面里的上升键，桌腿终于开始移动。

当时我没有急着试档位，先来回测试了几次升高、降低和松手停止。让桌子动起来只是第一步，能随时停住更要紧。

## 高度读出来了，桌子反而升不稳了

按键控制跑通后，我开始把高度解析搬进 ESP32-S3。离线分析已经能认出数码管段码，直觉上这一步只是把现成代码放进固件，结果真正麻烦的地方在 I²C 外设。

ESP32-S3 有两组硬件 I²C 控制器。我的桌子却需要在同一组 `CLK/DAT` 上处理五个从机地址：`0x24` 用于按键，`0x34` 至 `0x37` 对应四个数码管位置。一个硬件 I²C Slave 只能配置一个精确地址，两组控制器也没法直接接住这五个地址。

这里容易说岔。升降加高度需要的是五个地址，不是五组 I²C 线。物理上始终只有一对 `CLK/DAT`。

为了同时返回按键并接收高度，我把这段改成了软件 I²C。程序通过 GPIO 中断观察每一个时钟和数据边沿，自己判断 START、STOP、地址和 ACK。高度很快出现在 Web 页面上，桌子的上升却开始一顿一顿。它会升一小段，停一下，再接着升。下降最初比较流畅，继续修补以后也被拖下了水。

我先排查上层。Web 有没有提前发送 STOP，BLE 的运动租约有没有过期，高度刷新有没有误触安全上限，这些都查了一遍。日志里没有出现 `0x2E`，桌子仍然会短暂停止，问题只能继续往下找。

最后加上的计数很难看：三段日志一共发起 394 次按键响应，只有 20 次完整发送，另外 374 次中途终止。控制盒偶尔读到一个完整的 `0x47`，桌子就升一下；下一轮没读全，它便认为按键松开了。

软件 I²C 后面还试过边沿过滤、START 和 STOP 保护、调整任务优先级，甚至用 ULP 辅助采样。有些修改能让某一段日志好看一点，换个场景又会复发。Wi-Fi、BLE、日志和任务调度都可能挤进这段时序，继续打补丁只会让运动控制越来越难以收拾。

我最后把这套方案撤了。为了多读一个高度，把已经稳定的升降链路改得摇摇欲坠，实在舍本逐末。

控制盒侧重新使用硬件 I²C Slave，只处理地址 `0x24`，ACK、移位和时序都交还给 ESP32-S3 的硬件外设。这条路径此前已经在真桌上跑过连续升降和松手停止；最近的整合固件刚切回来，还要再烧录复验一遍。高度先留空，Web、手机和 Watch 上都显示一条横线，不用估算值凑数。

> [图片占位：软件 I²C 故障日志，标出发起次数、完成次数和 `abort`]

高度准备换一条路解决。我计划在桌板下方安装 TOF200C，让它朝地面测距，再加上安装位置的固定偏移，得到桌面高度。ESP32-S3 的另一组硬件 I²C 会单独连接这个传感器，不再碰控制盒的按键总线。

这部分目前只有方案，模块还没完成采购和真机验证。桌子的行程大约是 64 至 129 cm，传感器到货后要拿卷尺逐段校准，还得分别测试深浅地面、地垫、环境光和遮挡。数据稳定之前，档位闭环和最高高度限制都不会重新开放。

## 旋钮终于接上了

绕了一圈，最初想要的旋钮总算能用了。

我用 Karabiner 把旋钮的顺时针、逆时针和按下映射成三个闲置功能键，再由 Shell 脚本调用 ESP32-S3 的局域网接口。为了避免误碰一下桌子就突然动，第一个刻度只做准备，700 毫秒内出现第二个同方向刻度才开始升降。停止旋转后，最后一次指令的租约在大约 500 毫秒后失效，桌子自动停下。中途反向旋转则先停，再启动另一个方向。

同一套控制后来也接到了 Web、BLE 和 iPhone App。网页适合坐在电脑前使用，手机优先走 BLE，必要时再切到局域网。几种入口最终都调用同一套升降和停止逻辑，童锁、来源权限和断连停止也放在 ESP32-S3 里统一处理。

Apple Watch 的界面也已经做了一个版本。Digital Crown 很适合这种连续调节，正向旋转升高，反向旋转降低，停止旋转后发出 STOP。手表代码已经写完，单元测试和 Xcode 编译也通过了；真机配对、Crown 停止以及它和 iPhone、Android 同时连接的测试还没有做完，所以它现在仍是一张原型图和一套待验收代码。

语音也能复用局域网接口，不过我暂时没有急着往下接。没有可靠高度时，语音说“切换到站姿”还缺少闭环；只做“开始上升”又不如旋钮和实体按键踏实。等测距模块跑稳，再接 Siri 或 Home Assistant 会更合适。

## 现在还是一块挂在桌下的开发板

到这里，我手上的版本仍然是让 ESP32-S3 顶替原厂面板，两者不能同时接在控制盒上。桌子可以被网页、手机和旋钮控制，代价是原来的实体面板暂时退出。这种接法用来验证协议没问题，长期挂在桌下就有点顾此失彼了。

下一版会使用双 RJ45。北向接口连接升降桌控制盒，南向接口连接原厂面板，ESP32-S3 在中间转发数据。平时原厂按键和高度显示照常工作；收到 Web、BLE 或旋钮指令时，网关再插入相应键码。这样既不用牺牲实体面板，也能在原厂按键和无线命令撞车时做仲裁。

童锁也要等这一步完成才名副其实。现在的童锁只能拦住 Web、REST 和 BLE，挡不住直接接在控制盒上的面板。网关真正串到中间以后，才能过滤面板的升降操作，同时保留 STOP。

双 RJ45 的代码已经有一部分，实际透传还没跑通。两侧 GPIO、线序和上拉都量过，原厂面板一侧却还缺一份可靠的全上电波形。之前录到的文件与现场电压对不上，不能硬拿来当依据。等面包板接线整理好，我会重新抓一次面板侧的上升操作，再继续做透明透传。

> [图片占位：双 RJ45 方案草图，左边控制盒、中间网关、右边原厂面板]

如果这套结构跑通，后面才轮到更多桌型。Upsy Desky 的价值也在这里，它未必能直接控制我的桌子，但“把网关放在面板和控制盒之间”的办法很值得借鉴。我现在把不同厂商的协议收在 Desk Driver 里，自己的桌子先用 `yourdesk_v1`，以后碰到 UART、Loctek 或 Jiecang，再分别补对应的 Driver。上层的 Web、手机和蓝牙不需要跟着重写。

最后是 PCB。现在桌下挂着开发板、杜邦线和电阻，能用归能用，看起来仍然是一套实验装置。我还没有完整画过这种板子，准备先把双 RJ45、USB-C 供电、ESP32-S3 最小系统和保护电路塞进第一版原理图。首版不追求小巧，接口别画反、测试点留够、焊完能排查问题，就算开了个好头。

> [图片占位：桌下现有开发板原型，以及准备制作的 PCB 尺寸草图]

回头看，这件事和最初设想已经相去甚远。我只是想给桌子加一个旋钮，最后买了逻辑分析仪，拆了控制面板，记下了一堆十六进制键码，还因为贪心读取高度，把稳定的升降功能折腾坏了一次。

现在旋钮转起来，桌子已经会跟着动；手停下，它也会停。下一步先把原厂面板接回来，再处理高度和 PCB。至于把它做成一个真正的升降桌网关产品，等这些线不再挂在桌子下面时再说。

> 安全说明：本文记录的是我在自有设备上的协议分析和原型实验。升降桌运动可能夹伤人员或损坏物品，调试时应有人留在桌旁，并始终保留可靠的 STOP。文中的 RJ45 只是插头形态，不能接入电脑、交换机或普通网络设备。
